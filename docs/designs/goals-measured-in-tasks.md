# Design: Goals are measured in tasks, not sessions

Generated by /office-hours on 2026-09-04
Branch: staging
Repo: Hafeezrahman735/pomodoro-app
Status: APPROVED
Mode: Startup

## Problem Statement

The New/Edit Goal sheet asks for **Target sessions** (`tasks.tsx:927-931`), and
the form's own subtitle admits the number is unreliable: *"Estimated from your
25m default; sessions sized to a task estimate differ."* A goal set at 20
sessions counts down against blocks that are no longer 25 minutes each, because
`lib/sessionPlan.ts` sizes blocks to task estimates and the stopwatch records
whatever it records.

This is the same defect fixed in the daily goal earlier today, in a second
place. `daily-goal-in-time.md` explicitly ruled `Goal.targetSessions` out of
scope — *"a separate per-goal session target that stays session-based."* **This
document reverses that decision**, on the grounds that the argument which killed
session-framing for the daily goal applies here unchanged.

Two related gaps, both confirmed against the code:

| Ask | What exists today | What is missing |
|---|---|---|
| Link multiple tasks to a goal | `Task.taskGoalId` (`schema.prisma:251`), counted server-side by `loadGoalCounts` | Any way to link from the GOAL. The only path is task-side: open a task, tap the goal picker, pick one (`tasks.tsx:570`). Twelve tasks means opening twelve tasks. |
| A due date | `TaskGoal.deadline`, a `@db.Date` calendar day; renders red when past; sorts the hero card; appears in the calendar as `goal_deadline` | Anything that **tells** you. No reminder, no overdue state beyond a colour. The field is buried below the session stepper and its disclaimer, roughly a screen down in a modal. |

## Demand Evidence

Stated honestly: this is a single-user productivity app and the user is the
user, so there is no external demand signal and none is claimed. What there is:

- The user found this independently, one day after finding the identical defect
  in the daily goal — the second instance of the same class, spotted without
  prompting.
- The codebase already argues this case against itself. `tasks.tsx:1965`:
  *"Seconds, not session count: a 90-minute session and a 5-minute one are not
  the same amount of work and must not draw the same bar."* And the goal form's
  own disclaimer concedes the estimate is an estimate.
- `goalProgress.ts:22` already sets the precedent for the fix: `totalFocusSeconds`
  is documented as *"Reporting only, never a progress denominator."*

## Status Quo

A goal that groups a dozen tasks is assembled one task at a time, from the task
side, with no view of the goal while doing it. The goal's own screen can display
progress but cannot change what feeds it. If a goal was created with a session
target and no tasks, its progress bar tracks a number the app has admitted it
cannot measure accurately.

## Constraints

- `targetSessions` and `progressMode` appear in 6 backend files
  (`goalProgress.ts`, `taskgoals/routes.ts`, `notifications/handler.ts`,
  `middleware/eventBus.ts`, and two test files) — a small, fully-mapped surface.
- **No server cron exists.** Reminders must be local notifications on the
  device, following the `scheduleDailyReminder` / `applyDailyReminder` pattern
  in `mobile/services/notifications.ts`.
- Prisma enums cannot be dropped while rows reference them (learned on the
  `LEVEL` category during cleanup B2). `ProgressMode` therefore stays for now.
- New routes require an integration test against a real database (CLAUDE.md).

## Premises

1. A goal is a set of tasks with a due date. Sessions are effort spent *on* it,
   never the measure *of* it. — agreed (reverses `daily-goal-in-time.md`)
2. Progress is `completedTasks / linkedTasks`, computed now. Percentage stays
   primary on the card; the fraction is the secondary line. Adding a task
   honestly lowers the percentage. — agreed, amended by the user from a
   fraction-first proposal
3. Existing goals are converted, not reset. `targetSessions` becomes
   reporting-only; a goal left with zero linked tasks is flagged, never left
   silently at 0% and unachievable. — agreed
4. The due date gets a local reminder and a real overdue state. No server cron,
   no new push infrastructure. — agreed
5. Linking lives in the goal form as a multi-select, and the per-task goal
   picker stays. Two entry points, one relationship. — agreed

## Approaches Considered

**A — Form surgery only** (S/M). Delete the stepper, move the due date up,
collapse progress to tasks, add bulk linking. Rejected: leaves the due date
doing exactly what it does now, which the user identified as the real gap.

**B — The full pass, in dependency order** (M/L). **Chosen.** Server collapse +
bulk-link route + form rework + empty-goal flag + due-date reminder and overdue
state. No schema change in step 1.

**C — B plus a checklist screen** (L). The goal's detail screen becomes a live
checklist. Rejected as scope creep for now, and because a second surface that
toggles `isCompleted` is how state bugs start. The honest follow-on once B is on
device.

## Recommended Approach

**Revised by /plan-eng-review on 2026-09-04. Two branches, not one.** The
complexity check triggered at 10 files (really 13 — see finding 8), and Step 4
turned out to be a different architectural problem rather than a fourth step of
the same one: it needs dynamic notification identifiers where the app has only
ever used three fixed ones, a reconcile primitive that appears nowhere in the
codebase, and a `@db.Date`-to-local-fire-time conversion. Nothing is cut; the
order changed.

- **Branch 1 — Steps 1, 2, 2b, 3, 3b.** Everything below.
- **Branch 2 — Step 4.** Due-date reminders and the overdue state, tracked in
  `TODOS.md` with its five verified constraints.

Steps ordered so nothing depends on work that has not landed. Each ships and is
verifiable on its own.

### Step 1 — Server: progress collapses to tasks (no schema change)

`targetSessions` stays in the database and stops being a denominator. That is
what makes this step reversible: nothing is destroyed, so a bad call costs a
revert rather than a restore.

In `lib/goalProgress.ts`:
- `computeProgress` returns `taskProgress` as `overallProgress` unconditionally.
- `sessionProgress` becomes permanently `null`. Keep the field on
  `SerializedGoal` — the mobile `TaskGoal` interface is hand-maintained with no
  runtime validation on either side (`taskgoals/routes.ts:53-60` says so), and
  narrowing the wire shape is a worse change than leaving a null.
- `actualSessions` and `totalFocusSeconds` stay, as reporting stats. This is
  what the user gets in exchange for the stepper: effort spent is still visible,
  it just is not the goal.
- `resolveProgressMode` is deleted. `progressMode` always serializes `'tasks'`.
- Simplify the auto-complete guard from
  `if (c.linkedTaskCount === 0 && !goal.targetSessions) continue;` to
  `if (c.linkedTaskCount === 0) continue;`. Behaviourally identical — a goal
  with no linked tasks already computes 0% — but the old form reads as though
  a session target could still complete a goal, and it cannot.

In `modules/taskgoals/routes.ts`: `createSchema` and `updateSchema` keep
ACCEPTING `targetSessions` and `progressMode`; the values are stored and never
read. **Do not reject them.** An earlier draft of this document specified a 400,
which is wrong twice: Step 1 shipping before Step 3 would break every goal save,
and this is a mobile app that cannot be force-updated — an older binary on
someone's phone keeps sending the field indefinitely and would be permanently
unable to save a goal. Accept-and-ignore is the end state here, not a
transitional one. The field can be rejected only once no shipped build sends it,
which is the same conversation as dropping the column.

In `modules/notifications/handler.ts:156` and `middleware/eventBus.ts`: the
`task_goal.completed` copy currently *"describes whichever component(s) the goal
was measured on."* There is now one component; the copy becomes
"N of N tasks" and the `progressMode` / `actualSessions` / `targetSessions`
fields leave the event payload.

### Step 2 — Server: linking

**Deltas, not replace** (eng review finding 2). `POST /task-goals/:id/tasks`,
body `{ link: string[], unlink: string[] }`. The server touches only the ids it
was explicitly given.

An earlier draft specified `PUT` with replace semantics. That is a **data-loss
bug**, not a style choice. `loadGoalCounts` counts COMPLETED tasks toward a goal
(`goalProgress.ts:90-95`), so a goal reading "3 of 6" has three completed tasks
carrying its `taskGoalId`. Those never appear in an open-tasks picker, so they
would be absent from the payload, so replace semantics would clear them: the
goal drops from 3/6 to 0/3 on its first save. Archived recurring instances,
which inherit the template's `taskGoalId`, go the same way. Deltas make that
outcome structurally impossible rather than something the client must remember
to prevent.

**Creation becomes atomic** (finding 4): `POST /task-goals` accepts an optional
`taskIds` array and links in one transaction. An earlier draft created the goal
then attached tasks in a second call, with an explicit instruction not to roll
back — three outcomes for the form to handle, one of them a goal that silently
lacks the tasks the user just picked. One request removes that state instead of
handling it.

Rules, settled by the review (finding 7):
- an id appearing in BOTH `link` and `unlink` is a **400**. The client sent
  contradictory instructions; resolving it silently hides the defect.
- linking a task already attached to a different goal **moves** it.
  `Task.taskGoalId` is a single nullable column, so a task belongs to at most
  one goal, and picking it in this goal's form is unambiguous intent.
- because linking steals, `syncGoalCompletion` must run for the destination goal
  **and every goal that lost a task**.

Must also:
- verify the goal belongs to the caller (`findFirst({ id, userId })`, as PATCH
  and DELETE already do);
- verify **every** id in both arrays belongs to the caller before writing
  anything, via a new `userOwnsTasks(userId, taskIds)` helper placed beside its
  mirror image `userOwnsGoal` in `lib/goalProgress.ts` (finding 6). Reject the
  whole request if any id fails — a partial link on a bad id is worse than a
  clean 404.

Integration tests (CLAUDE.md, non-negotiable). The first two are REGRESSION
tests for the replace-semantics bug above and are not optional:
- **a COMPLETED task absent from the payload stays linked**;
- **an ARCHIVED recurring instance absent from the payload stays linked**;
- link adds, unlink clears; empty arrays are a no-op;
- a foreign `taskId` rejects the whole request with nothing written;
- a goal owned by another user returns 404;
- an id in both arrays returns 400;
- linking a task owned by another goal moves it and recomputes both goals;
- linking an already-done task trips `syncGoalCompletion` to 100%;
- `POST /task-goals` with `taskIds` links atomically, and a foreign id in that
  array leaves NO goal created.

New test file: name it so it does not collide with `stats.integration.test.ts`.
Note the `backend-integration-rate-limit` learning — the suite shares one
`127.0.0.1` bucket, and auth rate limiters skip only when `NODE_ENV=test`.

### Step 2b — The completion backfill (finding 3)

Step 1 makes a population of goals cross 100% for the first time. A `both` goal
with every task done but its session target unmet sits at `(1.0 + 0.5) / 2 =
0.75` today and becomes exactly `1.0` after the collapse. `syncGoalCompletion`
would then award `GOAL_COMPLETION_XP`, emit a `goal_completed` feed event and
push a notification for each one, drip-fed over days as the user next touches
each goal.

A one-time script, run with the deploy, completes that population **silently**:
no XP, no feed event, no notification. They are complete under the new rule, so
the state is honest — but the user finished that work weeks ago, and a lump of
XP that crosses a rank threshold with nothing on screen to explain it reads as a
bug. `--dry-run` first, and read the count, per CLAUDE.md's backfill rule.

Tests: dry-run writes nothing and reports the count; affected goals complete;
**no XP, no feed event and no notification are emitted**; a second run is a
no-op; already-completed goals are untouched.

### Step 3 — Client: the form

**The session input is removed from BOTH adding and editing a goal.** That falls
out of the structure rather than needing two fixes: `GoalFormModal`
(`tasks.tsx:846`) is a single component serving both paths — `goal === null` is
a create, otherwise an edit — routed through one `handleGoalSave`
(`tasks.tsx:2143-2144`). It is mounted twice, on the main Tasks screen
(`tasks.tsx:2523`) and inside the Goal Progress drill-down (`tasks.tsx:2235`),
and both mounts render the same component. Deleting the stepper therefore covers
all four combinations: create and edit, from either screen. There is no second
goal form anywhere in the app — verified by grep across the mobile tree.

In `GoalFormModal` (`tasks.tsx:846-975`):
- Remove `targetSessions` state, the stepper, `focusHours`, the disclaimer
  label, and the now-unused `sessionLengthMinutes` prop.
- Rename "Deadline" to "Due date", matching the task form's own wording, and
  move it above the new Tasks section.
- Add a **Tasks** multi-select as a NEW `components/TaskMultiSelect.tsx`
  (finding 5), not inline. `tasks.tsx` is already 2,528 lines and holds 10 of
  the 21 known React Compiler findings; `components/GoalStatsModal.tsx` is the
  extraction precedent. The picker pre-checks what is already linked and reuses
  `GoalPickerModal`'s visual language in reverse.

Create is now ONE request (`POST /task-goals` with `taskIds`), so there is no
half-created state to handle and no rollback question to answer.

**Known gap, accepted:** when linking moves a task off another goal, that goal's
progress silently drops and nothing tells the user. Option 7D would have
returned the losing goal names so the UI could say "moved from Thesis"; it was
not taken. Carried as a P2 task, not a blocker.

Also `goalSubMetrics` (`tasks.tsx:1333-1337`) drops its sessions clause.

### Step 3b — `lib/goalStats.ts` (finding 8, missing from the first draft)

A 330-line module the first draft never listed, dense with exactly the logic
being retired. Two places use `targetSessions` as a live denominator and would
render a retired target forever, since the column stays in the database and on
the wire:

- `goalStats.ts:128` — `Math.max(0, (goal.targetSessions ?? 0) - goal.actualSessions)`,
  a "sessions to go" remainder;
- `goalStats.ts:310` — an `actualSessions/targetSessions` stat cell.

Delete both. **Keep** bare session counts and focus time everywhere else — that
is premise 3 applied exactly: nothing that measures AGAINST a session target
survives, everything that REPORTS effort does. The status-line copy at `:182`,
`:195`, `:222` and `:240` already reads as reporting and stays.
`goalStats.test.ts` and `components/GoalStatsModal.tsx` come along.

Client types: remove `targetSessions` and `progressMode` from `CreateGoalInput`
(`goalStore.ts:71-78`), so nothing can send them again by accident. Leave them
on the `TaskGoal` interface (`types/index.ts:299-301`) — the server still
serialises both, and narrowing a hand-maintained wire type that has no runtime
validation is how `totalFocusSeconds` and `elapsedDays` got silently dropped for
months.

### Step 4 — Client: the due date does something

**Overdue state.** A goal past its due date gets an `OVERDUE` chip, pins to the
top of the goal list, and offers two actions: extend the date, or close the
goal. Today it gets red text and nothing else.

**Empty-goal flag.** `linkedTaskCount === 0` renders "No tasks linked" with a
tap-to-fix, on the card and in the list. This is the repair prompt for goals
migrated off a session target, and it is what stops premise 3 from being a
promise with no mechanism.

**Reminder.** A local notification ahead of the due date, following
`applyDailyReminder`. Reschedule on goal create/edit/delete and on hydrate.

Two constraints to design against, not discover:
- **iOS caps pending local notifications at 64**, shared with the daily reminder
  and the timer notifications. Schedule only the N soonest goal reminders
  (N ≈ 10) and reschedule on every hydrate.
- **Local notifications only fire on the device that scheduled them.** A goal
  created on another device will not remind here until this device reschedules.
  Reschedule-all-on-hydrate covers it; it is not instant, and that is the
  accepted cost of having no server cron.

## Open Questions

1. How far ahead does the reminder fire — the morning of, the day before, or
   user-configurable? Settings already has a daily-reminder time picker to
   follow. Deferred to implementation; pick one and state it.
2. Should a goal's due date warn when a linked task is due *after* it? The user
   explicitly did not ask for per-task roll-up. Noted, not scoped.
3. When does `ProgressMode` actually get dropped? It is dead after Step 1 but
   cannot be removed while rows reference it. Batch it with the other queued
   schema drops (`streaks`, `friendships`, `users.level`), not on its own.

## Success Criteria

- The goal form never asks for sessions, when ADDING a goal or when EDITING
  one, from either screen it can be opened from.
- A goal's progress equals its completed/linked task ratio on every surface.
- Linking twelve tasks to a goal takes one pass through one screen.
- No existing goal loses data, and no goal is left in a state where it can never
  complete — a goal with zero linked tasks says so and offers the fix.
- A goal with a due date produces a notification before that date, and reads as
  unmistakably overdue after it.
- An older app binary that still sends `targetSessions` can still save a goal.
  The value is ignored, not rejected.
- `resolveProgressMode` no longer exists.

The adversarial review pass on this document was performed by the same model
that wrote it, not an independent reviewer, because this session is configured

opinion. The Phase 3.5 cross-model second opinion was not run either. Two things

   turns out to be a common outcome, the right fix is a single endpoint that
   creates and links atomically.

## The Assignment

**Open your goals list and count how many have a session target set, and how
many of those have zero linked tasks.**

That second number is the population Step 1 converts. If it is zero, premise 3's
repair prompt is insurance and Step 4 can be built in any order. If it is not
zero, those are goals that would read 0% the moment Step 1 ships, and the
empty-goal flag stops being polish — it becomes the thing that has to land in
the same release, or people open the app to goals that look wiped.
