# Design: Recurring tasks in the Planning week list

Generated by /office-hours on 2026-09-04
Branch: cleanup/phase-d-rerenders
Repo: Hafeezrahman735/pomodoro-app
Status: APPROVED
Mode: Startup
Reviewed: 1 adversarial round; 5 issues found, all resolved below (initial score 6/10)

## Problem Statement

The Calendar > Planning tab's "THIS WEEK" section shows a recurring task once per
scheduled day, and labels any day before today as **Late**. A daily habit viewed
on a Thursday produces seven rows — three "Late", one "Today", three future — for
a single commitment.

This is the outcome the product was designed to avoid: a never-ending list of
missed recurring tasks. The Tasks tab avoids it; Planning did not.

**Introduced by** commit `08b79cf` (`lib/planningTasks.ts`). This is a regression.

## Root Cause

Two subsystems hold opposite, individually-correct rules:

| | Rule | Where |
|---|---|---|
| Tasks tab | A recurring task exists **only for today**. `spawn-recurring` archives every instance not due today, so a missed day leaves no row. | `backend/src/modules/tasks/routes.ts` |
| Calendar | A template is **projected across the whole requested range**, so the habit can be drawn on every scheduled day. | `backend/src/modules/calendar/routes.ts:205` |

The projection is right for a calendar. The defect is downstream:
`weekTasksToWorkOn` applies **one-off task semantics** to those projections, so
`item.date < todayKey` becomes `isOverdue → "Late"` (`planningTasks.ts:72`).

For a one-off task, overdue means still owed. For a recurring task, a past
occurrence is gone.

Aggravating: the range spans the **whole week including future days**
(`recurringProjection.ts:46-60`, `calendar.tsx:87-92`) and nothing dedupes by
`parentTaskId`. Dropping only past occurrences still leaves four rows for a daily
habit on a Thursday — so a "don't say Late" fix does not solve the flooding.

## Premises

1. The work list and the calendar's day/week views answer **different questions** —
   "what do I owe" vs "what was scheduled". The projection stays untouched. — agreed
2. A missed recurrence is not work you can still do, so it does not belong in a
   list of work to do. — agreed
3. A habit is one commitment, not N to-dos. — agreed

## Approaches Considered

### D1 — What a recurring task looks like in the list
- **Chosen: one row per habit, showing its next occurrence.** Past occurrences never appear.
- *Today and future only* — rejected: four rows for a daily habit on a Thursday; fixes the label, not the flooding.
- *Keep all, never label Late* — rejected: cosmetic, row count unchanged.
- *Exclude recurring entirely* — rejected: "what do I have to do this week" becomes incomplete.

### D2 — Where the collapse lives
- **Chosen: inside `weekTasksToWorkOn`.** The week's occurrences are already in the data Planning holds.
- *Fetch `/tasks/recurring`* — rejected: mixes two data sources in one list; adds a request for a fact the range response already answers.
- *Collapse server-side* — rejected: Day/Week views need the full projection, so this splits the one fetch feeding every calendar view.

## Recommended Approach

Change `mobile/lib/planningTasks.ts` only. One-off `task` items are untouched —
overdue still means Late.

**Ordering is load-bearing and must be as written.** The existing
`if (itemIsDone(item)) continue;` (`planningTasks.ts:65`) runs **first**, before
grouping. Completed occurrences are therefore gone before a habit's representative
is chosen. This is what decides the "today already done" behaviour — see
Resolved Question 1.

For `habit_instance` items, after the done-filter:

1. Group by `parentTaskId` (present on both real and projected occurrences —
   `types/index.ts:183`, `routes.ts:216,226`).
2. Drop occurrences dated before `todayKey`. A missed recurrence is not carried forward.
3. Keep the **earliest** remaining occurrence as the group's representative.
   (Steps 2 and 3 together already yield "today's if scheduled, else the next
   day this week" — no third condition is needed.)
4. A habit with no remaining occurrence this week drops out entirely. This falls
   out of step 2 and is intended.

Label the surviving row by its own date — "Today", or the weekday. Never "Late".

### Required alongside: the projected placeholder is missing fields

`weekTasksToWorkOn` reads `task.priority` and `task.isRecurring` directly off
`item.data` via an `as Task` **assertion** (`planningTasks.ts:67-79`), so TypeScript
cannot catch absent fields. The projected placeholder is deliberately narrow
(`routes.ts:217-230`) and carries only `id, title, parentTaskId, dueDate,
isCompleted, isProjected`. Consequences:

- `isRecurring: undefined` → falsy → the repeat icon is dropped
  (`PlanningView.tsx:277-279`), so the one row representing a habit does not read
  as a habit.
- `priority: undefined` → `PRIORITY_RANK[undefined] - PRIORITY_RANK[undefined]`
  is **NaN** (`planningTasks.ts:100`), and `NaN !== 0` is true, so the comparator
  returns NaN — undefined sort order among same-day rows.

**This is a present-tense bug**, already live for any future unspawned occurrence.
Today it is diluted across many rows per habit; after the collapse it becomes *the*
row for any habit whose next occurrence has not spawned — the common case.

**Fix, client-side, in the same function** (no server change, no payload growth —
the placeholder is narrow on purpose, 8000 objects across a 400-day range):

```
isRecurring: item.type === 'habit_instance' || task.isRecurring
priority:    task.priority ?? 'medium'
```

Deriving `isRecurring` from the item TYPE rather than a field that may be absent is
the more reliable of the two, and the type already guarantees it.

### Past-week navigation

Planning's week controls step the anchor by ±7 days (`calendar.tsx:126-132`), but
`todayKey` is always the real today (`PlanningView.tsx:225`). Browsing to a previous
week therefore makes every date `< todayKey`, so step 2 drops **every** habit while
one-off tasks in that week still show as "Late" — an inconsistent, unexplained
empty section.

**Decision: scope the section to the current week.** When the displayed week does
not contain `todayKey`, THIS WEEK is not a to-do list for a week you cannot act on.
Either hide the section for non-current weeks, or title it for the viewed week and
show occurrences without Late/overdue semantics. Pick one at implementation time;
silently dropping habits is the one outcome to avoid.

### Consequence to write down

The list **intentionally** stops matching the day-strip counts. The strip counts
per-day load and includes every occurrence (`PlanningView.tsx:207`,
`calendarItems.ts:124`); the list answers a different question. The comment at
`planningTasks.ts:12-17` currently frames that divergence as a bug to avoid and
**must be rewritten**, or it will read as one.

## Resolved Questions

1. **If today's occurrence is done, does the habit show its next day this week?**
   **Yes** — decided by step ordering, not preference. `itemIsDone` filters the
   completed occurrence before grouping, so the representative becomes the next
   remaining day. Recorded here because it is a product outcome falling out of an
   implementation detail; change the ordering if you want the opposite.

## Open Questions

1. Should the row carry a progress hint ("3 of 5 this week")? Restores what
   collapsing removes, at the cost of a second number. Deferred.
2. `isProjected` is absent from the mobile `Task` type (`types/index.ts:152-195`).
   Not required by this fix — the fallbacks above key off item type, not the flag —
   but it is the guard that stops a synthetic `projected:` id reaching a write path
   when these rows become tappable.

## Success Criteria

- A daily recurring task shows **exactly one row** in THIS WEEK, on any day of the week.
- No recurring task is ever labelled "Late".
- A one-off task overdue from Monday, viewed Thursday, **still** shows Late — no regression.
- A habit with no remaining occurrence this week does not appear.
- The single row shows the repeat icon **even when its occurrence has not spawned yet**.
- Same-day ordering is stable when a projected row is present (no NaN comparator).
- Browsing to a past week does not silently empty the habit list.
- Day, Week and Month views still show the habit on every scheduled day.

Tests in `lib/planningTasks.test.ts`: collapse by template; past-occurrence drop;
all-past-drops-out; **projected representative keeps `isRecurring` and a defined
`priority`**; one-off overdue unchanged.

There is deliberately **no** "prefer real instance over projected" test:
`projectRecurring` emits at most one occurrence per `(template, date)` with the
instance attached (`recurringProjection.ts:98-108`), so a same-day real+projected
pair cannot reach the client. An earlier draft of this document specified that
step; it was wrong.

## Dependencies

None. Self-contained in `mobile/lib/planningTasks.ts` and its test file, plus a
comment rewrite in the same file and possibly a label change in
`components/calendar/PlanningView.tsx`.

Sits on unmerged `cleanup/phase-c-storage-memory` and `cleanup/phase-d-rerenders`;
the Planning code it modifies is already on `staging`.

## The Assignment

Before writing the fix: **open Planning on a day when you have missed a recurring
task, and count the rows.** Confirm it is one per scheduled day across the whole
week, not just yesterday and today. If it is only two, the range or the projection
is narrower than this document assumes and the fix changes shape.

While you are there, check whether a habit scheduled **tomorrow** shows its repeat
icon. If it does not, you have seen the projected-placeholder bug live, before it
matters.

## What I noticed about how you think

- You said "this was exactly something I wanted to avoid" — you had already made
  this product decision and built it into the Tasks tab. The bug is not a missing
  decision; it is a second surface that did not inherit an existing one. That
  predicts where this class of bug appears next: any new screen that reads calendar
  items and treats them as to-dos.
- You guessed "yesterday and today" and were directionally right but conservative —
  it is the whole week. Trusting the symptom you can see is the right instinct; the
  range was the thing to check.
- You said "do not change or write code yet". That separation is what surfaced the
  seven-rows problem at all. A straight-to-code fix would have removed the "Late"
  label, shipped four rows instead of seven, and looked correct in the one demo
  case anybody would have tried.
