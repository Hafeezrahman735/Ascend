## Problem Statement

The focus timer reaches zero and makes no sound when the app is open.

This is not a missing feature. The alarm is already built: `timer_complete.wav`
sits in `assets/sounds/`, is registered in `app.json`'s expo-notifications
plugin, and is set as the Android channel sound. One boolean turns it off in
exactly the case where the user is most likely to be looking at the app.

`services/notifications.ts:45-48`:

```ts
const isForeground = AppState.currentState === 'active';
return {
  shouldShowAlert: !isForeground,
  shouldPlaySound: !isForeground,   // silent whenever the app is open
  ...
};
```

The comment explains the intent — avoid duplicating the on-screen Alert. The
defect is in what was compared: a **sound** was suppressed because a **modal**
was showing. A modal requires a glance. An alarm exists precisely for the moments
you are not glancing.

### Current behaviour, by posture

| Posture at zero | Signal today |
|---|---|
| App open, phone face-up on desk, user working elsewhere | Haptic buzz against a hard surface + silent modal. **No sound.** |
| Phone locked / face down / pocketed | OS notification fires `timer_complete.wav`. Works. |
| Phone in hand, watching the countdown | Silent modal. Adequate. |
| Backgrounded at any point, then returned | **Nothing at all** — see below. |

### Second defect (found during this session, not reported)

`app/(tabs)/focus.tsx:216-224` sets `backgroundedDuringRunRef` on any background
transition during a run. The completion handlers at `focus.tsx:262-268` and
`:271-277` then suppress both the haptic and the Alert when that flag is set, on
the assumption the user saw the OS notification.

If they did not — Do Not Disturb, ringer off, notification permission denied,
phone in another room — they return to a timer already sitting in `break` with no
acknowledgment that anything finished. The state machine reconstructs from
wall-clock anchors, so the transition happens silently on foreground.

**Precisely what the ref does**, because the first draft of this document got it
wrong: it is read in exactly two places (`focus.tsx:263`, `:272`) and gates
**only** `Haptics` + `Alert.alert`. It suppresses no notification. All timer
notification scheduling lives in `hooks/useTimerNotifications.ts`, which never
reads it.

## Demand Evidence

Weak, and worth stating plainly. This is the builder noticing a gap in their own
daily-use tool, not a user complaint. What raises it above a hunch:

- The user confirmed they hit **all three postures** depending on the session, so
  the silent case is not hypothetical for them.
- The asset and its entire delivery path already exist. Someone previously
  thought this mattered enough to bundle the WAV and wire two platforms.
- A pomodoro timer that does not make a noise when it finishes fails its single
  defining job. Table stakes, not differentiation.

No external user has asked for this. Treat it as correctness work.

## Status Quo

Users compensate by watching the countdown, or by backgrounding the app so the OS
alarm fires — which means the workaround for a focus app is to stop looking at
it. That is the wrong incentive for a product whose value is time away from the
phone.

## Constraints

- **Expo SDK 57**, React Native 0.86. `expo-av` is removed; `expo-audio` is the
  replacement. Verified API: `createAudioPlayer(source)`, `player.play()`,
  `player.pause()`, `player.seekTo(seconds): Promise<void>`, `player.remove()`,
  `setAudioModeAsync({ playsInSilentMode, interruptionMode })` where
  `InterruptionMode = 'mixWithOthers' | 'doNotMix' | 'duckOthers'`.
- The Android notification channel id `ascend-timer` is **immutable**. Changing
  it creates a second channel and loses every user's notification settings.
  Nothing here touches it.
- **`assets/sounds/timer_complete.wav` is 8.62 seconds long** (44.1 kHz stereo,
  380,160 frames). This is the single most consequential fact in the design — see
  "Stopping the alarm".
- Settings must round-trip through the existing `userSettingsStore` rather than
  inventing a second store.
- Ships alongside the pending production release; adds no schema change.

## Premises

1. The foreground silence is a bug, not a decision. Asset, plugin config and
   Android channel are already wired; one boolean disables it. **Verified.**
2. The dedupe compared the wrong two things — a sound suppressed because a modal
   was showing. **Verified.**
3. Returning after backgrounding gives no acknowledgment at all. **Verified**
   (`focus.tsx:216-224`, `262-268`).
4. A new dependency is *not* strictly required — an immediate local notification
   is a real alternative. Rejected on the silent-switch requirement, not effort.
5. The alarm must behave the same across all three postures. **User decision.**
6. The silent-switch override ships with its own off switch. **User decision.**

## Approaches Considered

### Approach A: `expo-audio` alarm module
New `lib/alarm.ts` owning the foreground completion sound. Satisfies the
silent-switch requirement via `setAudioModeAsync({ playsInSilentMode: true })`.
Leaves the backgrounded-return gap alone. Effort: S–M.

### Approach B: immediate local notification, no new dependency
Stop suppressing in the foreground handler; let the OS present the notification
even when active.

**Rejected**, and adversarial review found a second, worse reason than the one
this document originally gave:

1. Notification sounds obey the iOS ringer switch and Do Not Disturb, so it
   cannot satisfy the silent-switch override chosen this session.
2. `configureNotificationHandler` is the **global** handler for every
   notification the app receives. `notifications.ts:144` (daily reminder) and
   `:310` (goal reminders) both post to the `ascend-timer` channel, whose sound
   is `timer_complete.wav`. Flipping `shouldPlaySound` unconditionally means **a
   goal reminder arriving mid-session plays the timer completion alarm** — the
   app telling the user their session ended when it did not.

### Approach C: A, plus closing the backgrounded-return gap — **CHOSEN**

## Recommended Approach

**Approach C.** One alarm module, plus the missed-completion case.

Rationale: the two defects share a root cause — the app decides whether to signal
completion based on *where the app was*, rather than on *whether the user has
acknowledged it*. Fixing only the foreground half leaves the same reasoning error
one branch over, which is how it grows back.

### What does NOT change, and why

**`services/notifications.ts` is untouched.** The first draft of this design
changed `shouldPlaySound` to fire in the foreground *and* added `playAlarm()`.
That ships two sounds. Worse, it ships a **nondeterministic** double:
`useTimerNotifications.ts:44` cancels the pending notification the instant status
leaves `running`, and `complete()` moves `running → break`
(`stores/timerStore.ts:280`) at roughly the moment the OS fires it. Whether you
hear one alarm or two would vary run to run.

Leaving the handler alone fixes the double, the race, and the four-notification
regression above, all at once — and makes the change smaller than originally
specified. **`playAlarm()` is the only foreground sound.** The notification
remains the background path and nothing else.

### `mobile/lib/alarm.ts` (new)

Single owner of the foreground completion sound. **Foreground only** — expo-audio
playback is triggered from JS, and no JS runs while the app is suspended. Making
it work with the screen locked would need `shouldPlayInBackground` plus `audio`
in `UIBackgroundModes`, which this app does not declare and should not: an App
Store reviewer is entitled to ask what background audio feature a timer has.

```
playAlarm(prefs)   plays the WAV; no-op when prefs.enabled is false
stopAlarm()        pauses and rewinds; safe to call when not playing
releaseAlarm()     frees the native player (logout / teardown)
```

- Module-level singleton player, created lazily on first use and reused. A player
  per completion leaks native resources.
- `setAudioModeAsync({ playsInSilentMode: prefs.overrideSilentSwitch,
  interruptionMode: 'duckOthers' })` before playback. `duckOthers` is deliberate:
  a focus app's users have music or a podcast running, and an alarm that mixes
  underneath at equal volume is inaudible exactly when it matters.
- Every path is wrapped and logged. A failed alarm must never break the
  completion flow, which also writes the session to the server.

### Stopping the alarm

The WAV is **8.62 seconds**. After a focus completion the store sits in `break`
with the break not auto-started, so the user's next action is one tap on Start —
comfortably inside 8.62 s. Without a stop path the alarm plays over the beginning
of the next session, and `Alert.alert` dismissal does not stop audio.

`stopAlarm()` is therefore called from:

- `handleStart` and `handleResume` — starting new work silences the old alarm.
- The Alert's dismiss handler — acknowledging the completion silences it.
- Screen unmount.

This is why the original "play once, so no stop path needed" reasoning was wrong:
the stop path is a function of the asset's *length*, not of whether it repeats.

### `mobile/app/(tabs)/focus.tsx`

- Both completion handlers alarm — focus-done and break-over. They keep their
  distinct haptics (`notificationAsync` vs `impactAsync`).
- **The alarm fires only on a live completion.** On the backgrounded-return path
  the user gets the modal and haptic — the acknowledgment that was missing — and
  **no sound**. An alarm firing when you reopen the app forty minutes later is
  worse than silence.
- `backgroundedDuringRunRef` keeps its job of distinguishing the two, since it is
  the only thing that knows which case this is. It gains a comment saying what it
  actually gates, because the first draft of this design misread it.
- Stopwatch mode is unaffected: it never transitions `running → break`.

### Settings → Notifications

```
Session Complete      [ON ]     (existing)
Alarm sound           [ON ]     (new)
Play even on silent   [ON ]     (new, iOS only)
Daily Reminder        [ON ]     (existing)
```

- **Field names:** `alarmSound` and `alarmOverridesSilent` on `SettingsData`.
- **Both default `true`.** `alarmSound` because a timer should make a noise.
  `alarmOverridesSilent` because the person who silenced their phone in order to
  focus is this app's user, and they still need the alarm — that is the whole
  argument from the session, and it is the more aggressive default of the two, so
  it carries a comment in the store saying so.
- **`Play even on silent` renders on iOS only.** Android has no ringer-switch
  equivalent for the media stream, so `playsInSilentMode` changes nothing there.
  A switch that does nothing is a switch that lies.
- **Rendered conditionally, not greyed.** `SettingsRow` has no dimmed state, and
  the established pattern for a dependent row is conditional rendering (see the
  Reminder Time row, `app/settings.tsx:643-653`).
- **Relationship to "Session Complete":** that toggle gates *notifications*
  (`useTimerNotifications.ts:51`). `Alarm sound` gates the *in-app* sound. They
  are independent by design — one covers the case where you are away from the
  app, the other the case where you are in it — and each row's subtitle says so.

### `mobile/stores/userSettingsStore.ts`

Two booleans, device-local. **Both must be added to the explicit field list in
`update()` (`:136-149`)**, not only to `SettingsData` and `DEFAULTS` — that
literal is what gets written to AsyncStorage, so a field missing from it is set
in memory and silently forgotten on relaunch.

Both stay out of `PRIVACY_KEYS` / `NOTIF_KEYS` / `REMINDER_KEYS`, which is the
mechanism that makes a field device-local. `remindFocusMode` (`:24-32`) is the
precedent.

### Why these settings are device-local, not server-synced

`toBackendNotifPrefs` maps to the backend's `{ sessions, friends, achievements }`
categories, which gate **push notifications sent by the server**. An alarm sound
is a property of the device in your hand, not of your account — the right
behaviour on a tablet and a phone can differ. Syncing it would also mean widening
the `/notifications/preferences` Zod schema and touching `notificationPrefs`,
adding an API change to a release already carrying a schema transition.

**Consequence, stated plainly:** these two toggles do not follow a user to a new
device. Intended trade, not an oversight.

## Open Questions

1. **Does `playsInSilentMode` actually hold on iOS?** There are open Expo issues
   about `setAudioMode` params not applying correctly
   ([expo/expo#34902](https://github.com/expo/expo/issues/34902)). This must be
   verified on physical hardware before the setting is described to users as
   working. If it does not hold, the honest fix is to relabel the toggle, not
   ship a switch that lies.
2. **Is 8.62 seconds the right alarm length?** Almost certainly not — 2-3 s is
   conventional, would make the stop path far less load-bearing, and would cut
   the asset from 760 KB to roughly 200 KB. Not done here because it is the
   user's chosen sound and re-cutting it is a product decision, not an
   implementation detail. Recommended as a follow-up.
3. **The asset ships twice.** expo-audio loads it as a Metro asset via
   `require()`; the expo-notifications plugin separately copies it to the iOS
   bundle root and Android `res/raw`. The two mechanisms are not interchangeable.
   Fixing this means trimming the file (see 2), not restructuring the loading.

## Success Criteria

- Timer reaches zero with the app open and the phone on a desk → audible alarm.
- Audible in both postures — foreground and backgrounded. **Not** "same volume":
  notification sound uses the OS notification volume and expo-audio uses the
  media volume, which the user sets independently on both platforms.
- Exactly **one** alarm per completion, every time. No double, no coin flip.
- Ringer switch on silent, `Play even on silent` ON → still audible
  **(verify on a physical iPhone)**.
- Ringer on silent, `Play even on silent` OFF → silent, haptic only.
- `Alarm sound` OFF → no sound in any posture; haptic and modal unchanged.
- Alarm audible over music already playing; the other app's audio resumes after.
- Tapping Start while the alarm is playing silences it.
- Background through a completion, return to the app → modal and haptic, **no
  sound**.
- A goal reminder or daily reminder arriving mid-session does **not** play the
  timer alarm.
- Alarm failure does not prevent the session being written to the server.

## Distribution Plan

Existing pipeline. One caveat that matters for timing: `expo-audio` is a **native
module**, so this cannot reach existing users over the air — it needs the next
store build. That is the same build already required by the SDK 54 → 57 upgrade
sitting on `staging`, so it adds no new release constraint. It must not be
published as an `eas update` against the current 1.0.2 binaries.

## Dependencies

- `expo-audio` `~57.0.4` — installed.
- Independent of the pending production release, but should land on `staging`
  before the next store build is cut if it is to ship with it.

## Verification

No backend route is added or changed, so CLAUDE.md's integration-test mandate
does not apply. `lib/alarm.ts` decision logic (no-op when disabled, silent-switch
mode selection, stop-when-playing) is pure enough to unit test and is covered.
Everything involving actual audio output requires a physical device.

## What I noticed about how you think

- You asked "is there a sound that plays?" rather than "add a sound." That is a
  question, not a feature request — and it was the right instinct, because the
  answer was "yes, there is one, and it is switched off." A feature request would
  have produced a second alarm system beside the one you already had.
- You asked for the setting in the same breath as the fix. Building the escape
  hatch at the same time as the thing it escapes is a habit visible all over this
  codebase — the `accent` colour token, the accept-and-ignore fields on retired
  request params.
- Given the choice between one toggle and two, you took the one with full
  coverage. Same call as the week-strip fix and the transitional schema. You
  consistently pick the complete version when the incremental cost is small.
