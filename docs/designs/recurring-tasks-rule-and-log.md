# Design: Recurring tasks as a rule plus a completion log

Generated by /office-hours on 2026-10-27
Branch: staging
Repo: Hafeezrahman735/pomodoro-app
Status: APPROVED
Mode: Startup
Supersedes: none in substance. The previous design on this branch (hafee-staging-design-20261022-191215.md) covers time analytics.

## Problem Statement

A recurring task is stored today as a template row plus one copy ("instance") per due day. The app creates today's copy when it opens (`POST /tasks/spawn-recurring`), archives older copies, and keeps the streak, longest streak, total completions and lifetime focus as counters on the template. Ticking a copy changes those counters by hand.

Static read of the code (not a live test) found two defects that come from that design:

1. **A streak survives days the app was not opened.** A day the app was not opened has no copy, and the miss check looks only at the last copy made (`backend/src/modules/tasks/routes.ts:313-336`). Complete Monday, skip opening on Tuesday and Wednesday, open on Thursday: the streak carries on.
2. **Lifetime focus drifts.** Completing adds the copy's focus total at that moment (`routes.ts:541`). Focus logged after ticking is never added, and un-ticking subtracts the total as it is now (`routes.ts:554`).

The founder's question was whether the same feature could be built more simply. The founder chose to replace the copies with one row per recurring task plus a log of completed days.

## Demand Evidence

None yet. The founder's answer: recurring tasks are used by "a few users, lightly." No user has said they care about the streak. This design is justified by lower maintenance cost and correct numbers, not by user demand. The Assignment exists to find out what the real exposure is before building.

## Status Quo

Users with a recurring task see today's copy in the Tasks tab, tick it off, time it with the focus timer, and see a streak. Delete removes the whole recurring task (`mobile/app/(tabs)/tasks.tsx:2378`); there is no "skip today". The calendar draws past days from archived copies and future days from the schedule (`backend/src/modules/calendar/recurringProjection.ts`). Goal progress counts a recurring task as one item, done when its newest copy is done (`backend/src/lib/goalProgress.ts:174`).

## Target User & Narrowest Wedge

The target is the founder as maintainer first: 16 code files and 18 test files depend on the template/copy split today (files that mention `parentTaskId`, `parent_task_id` or `spawn-recurring`, counted with grep in `backend/src` and the mobile `app`, `lib`, `stores`, `components` and `hooks` folders). The user-facing wedge is a streak that is true. The way people use recurring tasks does not change; the numbers listed under Visible changes are corrected.

## Constraints

- Real users have production data. Every change to it needs a `--dry-run` on staging and then production, with the counts read before the real run (CLAUDE.md).
- Schema is applied with `prisma db push`, which Railway runs before deploy without `--accept-data-loss`. Additive, nullable changes are safe; a unique constraint or a dropped column must be applied by hand first.
- **Old app builds keep calling the old endpoints.** Version 2.0.0 binaries cannot receive the new code over the air, and 2.1.0 is not in the store yet. The backend must keep `spawn-recurring` and instance `PATCH` working until a minimum app version is enforced.
- Integration tests run against the local Postgres only.

## Premises

1. Both defects come from state kept by hand (counters, and copies that only exist on days the app opened) drifting from what actually happened.
2. The simpler model is one recurring-task row holding the schedule, plus a completion log with one row per day it was done. Streak, totals, missed days, calendar and goal progress are calculated from the log and the schedule. There is no daily copying, no archiving and no "last spawned" date. Skipped days count as missed automatically.
3. Users' raw history must come across exactly: every completed day, every focus session, and every session's focus time. This is checked by dry runs on staging and then production. Numbers calculated from that history are allowed to change, and the changes are listed under "Visible changes".
4. The way people use it does not change: today's recurring task is still a row you can tick off, time with the timer, edit, delete, and link to a goal.

### Visible changes (intended)

- Streak and longest streak drop for users whose streak survived days the app was not opened (defect 1).
- Lifetime focus becomes all focus time logged on the recurring task, including days that were never ticked off. Today it counts only focus on ticked days, as it stood at tick time (defect 2).
- Editing today's row edits the whole recurring task. Today an edit to the day's copy changes that day only. See Decisions.

## Cross-Model Perspective

An independent Claude subagent (no access to the conversation, could read the code) challenged premise 2 as Critical. Its argument: the completion log already exists. Archived copies are kept with their date and done state, and focus sessions point at them, so only the seven counter columns drift. Replacing the copies means re-pointing every past focus session and rewriting the goal-attribution SQL (`lib/goalAttribution.ts`, `lib/goalProgress.ts`, `lib/sessionAttribution.ts`, timer and calendar), which is the risky part. It also corrected premise 1: the skipped-day defect is fixed only if the streak walks the scheduled days, not by counting rows. Its 48-hour suggestion was to keep the copies, stop writing the counters, and calculate the numbers from copies and sessions.

The founder kept premise 2 as stated.

## Approaches Considered

- **A: Calculate from the existing copies.** Small, no migration. Ruled out: keeps the daily copying the founder wants gone.
- **C: Create a day's row only when it is used.** Medium; removes the daily job without moving sessions. Ruled out by the founder in favour of the full model.
- **B: Rule plus completion log.** Chosen.

## Recommended Approach

Approach B, shipped in stages. Each stage leaves the app working, is pushed to staging, and is checked there before the next one. Stage 1 starts only after the stage 0 decision rule says go.

### Target model

- **The recurring task.** A `Task` row keeps `isRecurring`, `recurringDays`, `dueDate` (the inclusive "repeat until"), time slot, goal, tags, priority and `order`. Its schedule history lives in a new table, `RecurringSchedule`: `taskId`, `recurringDays` and `effectiveFrom` ('YYYY-MM-DD'). A row is added whenever `recurringDays` changes, effective from the user's local today. Existing tasks get their first row rebuilt from their own history: `recurringDays` = the weekdays their copies fell on (all seven means every day), effective from their creation day. If that differs from their current days, a second row with the current days takes effect from the backfill day. A weekday a task was never scheduled on therefore never becomes a false miss. A weekday that was scheduled only briefly may still be judged across the whole earlier period, which the stage 2 comparison accepts as cause 4. Creating a recurring task (`POST /tasks`) or switching a task to recurring (`PATCH /tasks/:id` with `isRecurring`) writes its first row, effective from the local creation day. When no row covers a day, the calculation uses the task's current `recurringDays`. The schedule backfill is idempotent and is run again after the code that writes rows is live, to cover tasks created in between. Integration tests: creating a recurring task writes its first row, and a `recurringDays` edit writes a new one.
- **The completion log.** A new table, `RecurringCompletion`: `id`, `userId`, `taskId` (the recurring task), `date` ('YYYY-MM-DD', the user's local day, the same convention as `Note.date`) and `completedAt`. It is unique on (`taskId`, `date`).
- **Sessions.** A focus session on a recurring task has `taskId` = the recurring task. Its day is the session's `localDate`. A new nullable column, `occurrenceTaskId`, keeps the copy a session originally pointed at, so the move can be undone.
- **"Today" for the server.** The server's idea of today always comes from the client. Every call that needs the user's local today takes a `localDate` parameter (query string or body), which is already how `GET /tasks/recurring`, `POST /tasks` and `spawn-recurring` work. A missing or invalid value falls back through `resolveLocalDate`, as it does now.
- **Calculated, never stored:**
  - **Streak:** walk back through the days from yesterday, or from today if today has a log row. Each day is judged against the schedule in force on that day: the `RecurringSchedule` row with the latest `effectiveFrom` on or before it. A day counts as scheduled if `lib/recurrence.isScheduledOn` says so under that schedule, it is on or after the task's local creation day, and it is on or before the repeat-until day.
    - A schedule edit therefore neither breaks nor extends a streak.
    - The walk stops at the first scheduled day with no log row.
  - **Longest streak:** the same rule over the task's whole history.
  - **Total completions:** a count of log rows.
  - **Lifetime focus:** the sum of `durationSeconds` of focus sessions on the recurring task. Until the stage 5 precheck passes, this also includes sessions whose `taskId` is one of its copies, found through `parentTaskId`.
  - **Goal progress:** a recurring task counts as one item. It is done when a log row exists for its most recent scheduled day on or before the user's today. That is today if it is scheduled today; otherwise the last scheduled day before it, or the repeat-until day's last occurrence once it has ended. This matches today's "newest copy is done" rule, except that a day the app was not opened now counts as not done, which is intended.
- **Which shape each client gets.** `GET /tasks` returns today rows only when the client sends `occurrences=1`, which only the stage 4 build does. In that response the copies are left out. Without the flag the response is unchanged: copies only, no today rows. So no build ever sees the same recurring task twice. `PATCH /tasks/:id` that sets `isCompleted` on a recurring task itself (not a copy) is rejected with 400; ticking always goes through a copy or the completion endpoints. Integration tests cover both response shapes and the rejected `PATCH`.
- **Today's row** in `GET /tasks?localDate=&occurrences=1` is one entry per recurring task due today. Its `id` is the recurring task's own id, with two extra fields: `occurrenceDate` (today) and `isOccurrence: true`. There is no compound id to parse. Every action maps to an existing id:

  | Action on today's row | Endpoint |
  |---|---|
  | Tick off / un-tick | `PUT` / `DELETE /tasks/:id/completions/:date` |
  | Edit | `PATCH /tasks/:id` (edits the whole recurring task) |
  | Delete | `DELETE /tasks/:id` (ends it, as today) |
  | Start the timer | session `taskId` = `id` |
  | Open details or stats | `GET /tasks/:id`, which returns the calculated streak, longest streak, completions and lifetime focus |
  | Link to a goal | `PATCH /tasks/:id` `taskGoalId` |
  | Reorder | `order` on the recurring task |

### The completion endpoints

`PUT /tasks/:id/completions/:date` and `DELETE /tasks/:id/completions/:date`, with `localDate` in the body.

- **404:** the task does not exist, is not the caller's, is not recurring, or is archived.
- **400:**
  - `date` is not a valid 'YYYY-MM-DD';
  - `date` is not a scheduled day for the task;
  - `date` is before the task's local creation day or after its repeat-until day;
  - `date` is later than the client's `localDate`;
  - `date` is more than one day earlier than it. This matches the 24-hour back-dating limit already applied to sessions (`MAX_BACKDATE_MS`).
- **Idempotent:** a `PUT` on a day already done, or a `DELETE` on a day not done, returns 200 and changes nothing.
- **Side effects run through one shared function, `applyCompletionChange(userId, taskId, date, done)`,** used by both these endpoints and the copy `PATCH`. It runs only when the log row actually appears or disappears:
  - award or revoke XP and `tasksCompleted` exactly as the copy `PATCH` does now, as a true undo;
  - emit the `task_completed` feed event on completion;
  - call `syncGoalCompletion` for the task's goal;
  - while copies still exist (stages 1-4), also mark today's copy for that date as done or not done, so an older build on another device shows the same state.
  Because the side effects key on the log row, a tick from either path never pays XP twice.
- **Integration tests against the local database:**
  - success and idempotent repeat for each verb;
  - 404 for another user's task, a non-recurring task and an unknown id;
  - 400 for a malformed date, an unscheduled day, a future date, a date older than one day, and a date past the repeat-until day;
  - XP granted once and revoked once;
  - a feed event on completion;
  - goal progress changing.

### Decisions

- **Edits to a single day are dropped.** Editing today's row edits the whole recurring task. Per-day title or time-slot edits on existing copies are discarded at stage 5. Titles as they were survive on each session's `taskLabel`, so time reports keep their names.
- **Schedule changes:** each day is judged against the schedule in force that day (`RecurringSchedule`). Edits made before the table exists cannot be recovered, so the stage 2 comparison accepts them as an explained cause.
- **Lifetime focus counts all focus time**, including days not ticked off (listed under Visible changes).

### Stages

0. **Measure and decide (the Assignment).** Read-only counts on production, then the decision rule:
   - **Proceed with B** if fewer than 10,000 focus sessions point at copies.
   - **Stop and choose again between B and C** if there are 10,000 or more. At that size, moving sessions has a real risk and C avoids it.
   - **In-app note:** if any owner says they watch their streak, stage 2 ships with a one-time note explaining the correction. Otherwise it ships silently.
1. **Add the log and write to it from both paths, and start counting app versions.**
   - **Tables:** add `RecurringCompletion` and `RecurringSchedule`, and backfill one schedule row per existing recurring task (`--dry-run` first). From here on, `PATCH /tasks/:id` adds a schedule row whenever `recurringDays` changes. Before pushing, check with `prisma migrate diff` whether creating the new table with its unique constraint triggers a data-loss warning. If it does, apply it by hand on staging and then production; if not, let the pre-deploy push apply it.
   - **Two-path writing:** the copy `PATCH` now runs `applyCompletionChange`. On un-complete, it removes the log row only if no other completed copy exists for the same parent and day.
   - **Backfill** (`--dry-run` first): one log row per completed copy. `date` = the copy's `dueDate` formatted as UTC 'YYYY-MM-DD' (spawn stores the client's day at UTC midnight, so this round-trips). It uses insert-on-conflict-do-nothing, and the dry run reports duplicate completed copies per day.
   - **App versions:**
     - The 2.1.0 native build, already needed for the SDK 58 upgrade, ships before stage 1 ends with two additions:
       - every request sends `X-App-Version`;
       - at launch the app calls `GET /app/config` and, when it is older than `minAppVersion`, shows a blocking "Update Ascend" screen with a store link.
     - This is the earliest build that can ever be told to update. 2.0.0 builds never can.
     - The server records, per user, the latest version seen and the time it was seen. A request with no header or an unreadable one is recorded as "old".
   - **Readers:** nothing reads the log yet.
2. **Read from the log.**
   - Streak, totals, lifetime focus (sessions on the task plus its copies), goal progress and the calendar switch to the calculations above.
   - **Comparison:** a staging script prints, per recurring task, the stored counters against the calculated ones. Every difference must come from one of four causes:
     1. defect 1;
     2. defect 2;
     3. the lifetime-focus definition change;
     4. a schedule edit made before `RecurringSchedule` existed, including a briefly scheduled weekday now judged across the whole rebuilt period.
   - **Gate:** any other difference blocks the stage.
3. **Re-point sessions.**
   - Add `Session.occurrenceTaskId`. The backfill (`--dry-run` first) does three things for every session whose `taskId` is a copy:
     1. copy that id into `occurrenceTaskId`;
     2. fill a null `localDate` from the copy's `dueDate`, marked approximate;
     3. set `taskId` to the copy's parent.
   - **Dry run reports:** per-user session counts and focus totals before and after, which must be identical, and how many sessions had a null or approximate `localDate`.
   - **New sessions from older builds:** from this stage on, the session-create path (`POST /timer/complete`) maps a copy id to its parent the same way, keeping the copy id in `occurrenceTaskId`. Sessions from older builds that still time copies therefore land on the recurring task too.
   - **Goal SQL:** `SESSION_GOAL_JOIN`/`SESSION_GOAL_EXPR` keep the parent join until stage 5.
4. **Switch the app.**
   - **The new build:**
     - uses the today rows and the completion endpoints, and the timer sends the recurring task's id;
     - sends `occurrences=1` on `GET /tasks`;
     - already reports its version and checks `minAppVersion`, since 2.1.0.
   - **Older builds:** the backend keeps `spawn-recurring` and the copy `PATCH` working for them, and their writes reach the log through `applyCompletionChange`.
   - **Release:** this requires a new native build, made by the founder (the runtime version follows the app version).
5. **Remove the old machinery.**
   - **Trigger:**
     - **Metric:** the share of users active in the last 14 days whose latest recorded version is older than the stage 4 build, or "old" (no header).
     - **Fires when** that share stays under 5% for 14 days in a row, or 60 days after stage 4 ships, whichever comes first.
     - **Then** set `minAppVersion` to the stage 4 build: 2.1.0 and later builds are told to update.
   - **Accepted outcome for 2.0.0 builds still in use:**
     - removed endpoints answer 426 with "Update Ascend to keep using recurring tasks", which those builds show as an error;
     - their recurring tasks stop appearing;
     - the rest of the app keeps working.
   - **Mitigation:** stage 0's owner list shows who is affected, and they can be messaged first.
   - **Precheck:** run the stage 3 re-point once more, with a dry run. Zero sessions may still reference a copy.
   - **Then:**
     - simplify the goal SQL to the task's own goal;
     - delete the spawner, the copies and `parentTaskId`;
     - drop the template counters (`recurring_streak`, `longest_streak`, `total_completions`, `total_focus_time_ms`), `last_spawned_date`, and the copies' `lifetime_*` columns.
   - **Schema change:** this is destructive, so it is applied by hand on staging and then production, with `prisma migrate diff` confirming each.

## Open Questions

- **Timezone of a completion date.** The date is the client's local day at tick time, so a user who travels could log completions in two zones for what feels like one day. This matches how sessions are dated today, and is accepted unless the stage 0 counts suggest otherwise.
- **"Skip today".** The log makes this easy: a skipped-day row that does not break the streak. It is out of scope unless a user asks.
- **Stats modal timing.** The modal reads calculated numbers from `GET /tasks/:id`, loaded per user in 2 queries over the whole history (R6). Measure on staging after stage 2.

## Success Criteria

- **Integration tests** against a real database show that:
  - a skipped scheduled day (app not opened) breaks the streak;
  - focus logged after ticking is counted in lifetime focus;
  - the completion endpoints behave as specified, including every failure case listed.
- **Stage 3, dry run and real run:** per-user session counts and total focus time are identical before and after.
- **Stage 2 staging comparison:** every difference between stored and calculated numbers comes from one of the four listed causes.
- **Before stage 5:** zero sessions reference a copy.
- **After stage 5:** no code path references `parentTaskId` or `spawn-recurring`, and the calendar and goal outputs on staging match stage 2.

**Problem**

### Failure modes
- **Two devices tick at once:** the unique key makes the second insert a no-op, so XP is paid once (concurrency test). Not silent.
