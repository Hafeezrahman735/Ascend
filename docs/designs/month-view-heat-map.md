## Problem Statement

The month heat map appears not to work. It does not work, but not for the
reason it looks like — **it has never actually been tried.** Two defects mean
the version on screen is not the design anyone approved:

1. **It renders three of its four steps.** `cellColors` gives `light` and
   `empty` the same background (`Colors.raised`); only the date-number colour
   differs. A four-level scale reads as three.

2. **Load is defined as booked MINUTES only.** `dayLoad` sums
   `itemTimeRange`, and `itemTimeRange` (`lib/calendarItems.ts:194-210`) returns
   null for anything without a clock — every untimed task, and every
   `goal_deadline`. Those fall to a count-based fallback that only distinguishes
   "3 or more" from "fewer", so a day holding one goal deadline scores `'light'`,
   which per defect 1 is invisible.

The consequence: **the one item type with a hard, unmovable date contributes
nothing to the map, and a day of three untimed tasks barely registers next to a
single two-hour meeting.** Judging "density does not tell me anything" against
that implementation is judging a bug, not a design.

## The trade being accepted, explicitly

A heat map shows **how much**, not **what**. After the fix, a goal-deadline day
reads as occupied — but still not as a *deadline*. That is not a defect to be
solved later; it is what choosing a single visual channel means. Recorded here
so nobody reopens it in three months believing it was an oversight.

## Premises

1. Density is the right question for this screen; the implementation was the
   problem, not the concept. — agreed
2. Every commitment contributes weight, not only clocked ones. An untimed task
   is still work; a deadline is still a claim on the day. — agreed
3. Notes and to-dos contribute ZERO. The existing principle stands: "a jotting
   is not weight." — agreed, unchanged from the current code
4. The grid shows load and not composition, and that is accepted. — agreed

## Rejected

- **Markers over shading** (flag for deadlines, edge bar for events, dot for
  to-dos). Designed in full earlier the same day and reversed by the user as too
  complex. The stronger reason for dropping it: it was compensating for a broken
  instrument rather than repairing it. Two of its three markers exist only
  because untimed items score zero, which this design fixes at the source.
- **Hue + intensity** — background colour carries the dominant type, intensity
  carries load. Rendered, and better than expected. Rejected because "dominant
  type" on a day holding a task, an event and a deadline is an invisible
  tie-break rule the user must learn, mixed days are the common case rather than
  the exception, and it fails in greyscale and for red-green colour blindness.
- **Minimal repair** — fix the two defects, keep minutes-only load. Rejected
  because the render shows the grid still clustering in the middle: it corrects
  the lie without making the scale useful.

## Recommended Approach

Revised by /plan-eng-review on 2026-09-06. Five decisions folded in; two of them
fixed defects the design would have shipped.

Every non-note item contributes weight. Five steps instead of four.

```
weight(item) =
  timed task / event    -> its duration in minutes
  untimed task          -> UNTIMED_TASK_WEIGHT     (30)
  habit_instance        -> HABIT_WEIGHT            (30, FLAT — see below)
  goal deadline         -> DEADLINE_WEIGHT         (90)
  all-day event         -> ALL_DAY_EVENT_WEIGHT    (180)
  note / to-do          -> 0

day total -> free | light | some | heavy | full
             0      <60     <150   <300    300+
```

**Habits are weighted FLAT, ignoring their times** (review finding 2). A
projected future occurrence is a deliberately narrow placeholder carrying no
`startMinutes` (`backend calendar/routes.ts:217-228` — "The calendar only reads
title and isCompleted"), so weighting by duration would make today's spawned
habit heavier than the identical habit next Tuesday, and next Tuesday would
silently darken when it spawns. Flat weight keeps the grid stable.

  Accepted cost, stated plainly: a two-hour daily habit now weighs the same as a
  five-minute one. That is the same equal-treatment-of-unequal-work problem this
  design exists to fix, accepted here to avoid a number that changes on its own.
  Revisit if long habits become common.

**All-day events get their own weight** (review finding 4). `itemTimeRange`
returns null for an `event` with both minutes null (`:206`, the explicit all-day
case) and for external Google/Apple events with `isAllDay` (`:212`). Unweighted
they would compute to zero and render FREE — worse than today, where the count
fallback at least gives them 'light'. A conference is the largest claim a day
can carry.

The count-based fallback disappears. It existed only because untimed items
scored zero, and it was never a real measure — it distinguished "3 or more" from
"fewer" and nothing else. **Deleting it is provably safe only because every
non-note type now has a non-zero weight**; that is the invariant the fallback
was patching, and the `itemWeight` tests below pin it.

### Changes

1. **`lib/calendarItems.ts`** — add `itemWeight(item): number` beside
   `itemTimeRange`, composing it for the timed cases. The four weight constants
   live here too and are EXPORTED (finding 3): a test asserting the literal 30
   breaks the moment you tune it, and tuning is expected.
2. **`MonthView.tsx` `dayLoad`** — compute `load` from summed `itemWeight`, and
   keep `bookedMinutes` as real clocked time from the existing `bookedMinutes()`
   helper (finding 1). **These must stay separate.** `dayLoad` returns both, and
   the panel prints the second one as "booked" (`:225`). Summing weight into it
   would make a day with one untimed task print "30m booked" when nothing is
   booked — a fabricated number replacing the old missing one.
3. **`MonthView.tsx` `Load` type + `cellColors`** — five levels, five distinct
   backgrounds. `free` must be visibly darker than `light`; they currently share
   one colour, which is defect 1. The four THRESHOLDS stay in this file
   (finding 3): how many shades of purple is a rendering decision the lib has no
   business knowing.
4. **Legend** — show all five steps. It currently shows two.
5. **`accessibilityLabel`** — say the load level in words. It currently reads out
   raw hours, which is now only part of the weight.
6. **Header comment** — rewrite. It argues that shading beats per-type dots,
   which is still true and worth keeping, but it does not mention that shading
   was only counting a third of what is on the day.

### Tests

`lib/calendarItems.test.ts`, mirroring the existing `bookedMinutes` describe at
`:189`. Reference the exported constants, never the literals.

- every branch of `itemWeight`: timed task, untimed task, habit (timed AND
  projected — same result, which is the point of finding 2), goal deadline,
  timed event, all-day event, external all-day, note
- **no non-note type returns 0** — the invariant that makes deleting the count
  fallback safe
- notes and to-dos return 0
- `bookedMinutes` is unchanged by any of it: a day of untimed tasks still books
  zero minutes

### The numbers are invented — this is the main open risk

`UNTIMED_TASK_WEIGHT = 30`, `HABIT_WEIGHT = 30`, `DEADLINE_WEIGHT = 90` and
`ALL_DAY_EVENT_WEIGHT = 180` are calibration constants chosen to make the render
look right, not derived from anything. They are the part of this design most
likely to be wrong, and they are cheap to change: four exported constants in one
file. Ship them, look at a real month, adjust.

The specific failure to watch for: if `DEADLINE_WEIGHT` is too high, a day whose
only item is a deadline reads as busier than a day with two real hours of work,
which is a new lie replacing the old one.

Tracked in `TODOS.md` so it outlives this doc being read.

## Success Criteria

- A day holding only a goal deadline is visibly not empty.
- A day of three untimed tasks reads heavier than a day with one 30-minute item.
- All five steps are distinguishable on a real screen, and the legend names all
  five.
- A month with real data uses more than the middle of the scale.
- Notes still contribute nothing.

## Dependencies

`mobile/components/calendar/MonthView.tsx`, `mobile/lib/calendarItems.ts`
(+ `calendarItems.test.ts` for `itemWeight`).

Client-only. No schema change, no route change, no new data. `itemWeight` is a
pure function and belongs under test — the weights are the risky part and a test
pins what each type contributes.

## The Assignment

**Open your calendar and count how many days this month hold work with no clock
time on them** — a task you gave a due date but never scheduled a time for, or a
goal deadline.

That number is how much of your month the current heat map cannot see. If it is
zero, this design changes almost nothing for you and the map was already telling
you the truth. If it is most of them, then the map has been showing you a third
of your month and calling it a workload.

## GSTACK REVIEW REPORT

Reviewed by /plan-eng-review on 2026-09-06. Status: DRAFT -> REVIEWED.

### Verdict

Sound, and better than the doc it supersedes. Two of the five decisions fixed
real defects rather than tightening wording:

- **Finding 1** would have shipped a fabricated number to the screen. `dayLoad`
  returns `bookedMinutes` and the panel prints it as "booked"
  (`MonthView.tsx:225`). The doc said "sum `itemWeight` instead of
  `itemTimeRange`" without noticing the second return value, so a day holding one
  untimed task would have printed "30m booked" on a day with nothing booked. This
  design exists to stop the month view lying; it nearly moved the lie into the
  detail panel.
- **Finding 4** would have made all-day events render FREE. `itemTimeRange`
  returns null for a two-null `event` (`:206`) and for an external `isAllDay`
  (`:212`). With the count fallback deleted and no weight assigned, a conference
  would compute to zero — strictly worse than today, where the fallback at least
  scores it 'light'.

### Answering the three things this review was asked to focus on

1. **The invented constants.** They are the right risk to have flagged, and the
   flag was under-counted: there are four of them now, not two. Nothing here can
   validate them — they encode a judgement about how much a deadline weighs, and
   only a real month answers that. Mitigations taken: exported (so tests do not
   hardcode them), all in one file, and a `TODOS.md` entry naming the concrete
   symptom of getting them wrong. That is the whole of what is available before
   shipping.
2. **`itemWeight` and its test coverage.** A pure function over a discriminated
   union with 8 branches and zero tests as drafted. Coverage is now specified
   under Tests, mirroring `calendarItems.test.ts:189`. The test that matters more
   than the per-branch cases is "no non-note type returns 0" — see below.
3. **Deleting the count fallback.** Safe, but NOT unconditionally, and the doc as
   drafted did not state the condition. The fallback is what currently keeps
   zero-duration items off the FREE shade. Deleting it is only safe while every
   non-note type carries non-zero weight — which was FALSE in the draft, for
   all-day events. It is now true by construction and pinned by a test. That
   invariant is the finding; the deletion itself was never the risk.

   Day shapes checked against the deletion: only untimed tasks (covered, 30
   each); only a deadline (covered, 90); only notes (0 -> FREE, correct and
   unchanged); only an all-day event (was the hole, now 180); projected vs
   spawned habit (equal by design, finding 2); mixed timed and untimed (sums
   cleanly).

### Performance

No issues. `dayLoad` runs 31 times per render over a handful of items each;
`itemsByDate` is a Map; `itemWeight` is O(1). Same asymptotics as today, so not
worth memoising. `MonthView` is unmemoised and re-renders on unrelated store
changes, but that is `cleanup/phase-d-rerenders` scope, not this change.

### NOT in scope

- Showing WHAT is on a day. Settled in the doc under "The trade being accepted".
- Weighting habits by duration. Decided against (finding 2), with the cost stated.
- Any backend change. The projected-habit payload stays narrow; the client
  accommodates it rather than the route widening.
- Memoising `MonthView`.
- Tuning the constants before shipping.

### What already exists and is being reused

- `itemTimeRange` (`calendarItems.ts:194`) — `itemWeight` composes it rather than
  reimplementing it.
- `bookedMinutes` (`:289`) — already exported, already used by
  `PlanningView.tsx:206`, now also the honest source for the panel's "booked".
- `countsTowardLoad` (`:302`) — the notes-are-not-weight rule, unchanged.
- The `describe('bookedMinutes')` block at `calendarItems.test.ts:189` — the shape
  the new tests copy.

### Failure modes

| Failure | Detection | Response |
|---|---|---|
| A new `CalendarItem` type is added with no `itemWeight` branch | The "no non-note type returns 0" test fails | Add its weight; never default it |
| Deadlines shade too heavy | A deadline-only day reads darker than a genuinely busy one | Lower `DEADLINE_WEIGHT`; one line |
| Everything clusters at one shade again | A real month uses only two of the five colours | Move the thresholds, not the weights |
| Projected habits shade differently from spawned ones | The same habit changes shade when today rolls over | Regression in finding 2 — the flat-weight branch was bypassed |

### Parallelization

Not worth splitting. Three files, one of them a test file, all client-side. The
lib change gates the view change; do them in that order in one pass.
