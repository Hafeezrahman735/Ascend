## Problem Statement

The founder, in their own words: "I could stay busy all day without having a clear picture of where my time actually went or how much effort I was putting into individual projects."

Ascend records what actually happened (every focus session stores its task, goal, local date and local hour) and what was planned (a task's scheduled block, `Task.startMinutes`/`endMinutes`, and its `estimatedMinutes`). The two never meet. The calendar draws the plan and none of the sessions, and nothing compares them. The goal-level comparison already exists (planned time, pace and minutes per day to finish, `backend/src/lib/timePace.ts`); the day and week comparison does not.

Measurable restatement: each day, Ascend shows whether the hours went to the work that was planned, or got spent on something else.

## Chosen Approach (B, founder's choice)

### Day view: overlay (founder chose overlay over two lanes)

```
CALENDAR · DAY (Thu 31 Oct)
┌──────────────────────────────────────┐
│ Planned 3h · Focused 1h 30m          │
│ 38m of it on unplanned work          │
├──────────┬───────────────────────────┤
│  9:00    │┌────────────────────────┐ │  Planned block: outlined.
│          ││Write case study 9–11 █ │ │  Focus on the SAME task fills it from
│ 10:00    ││████████  52m       ░░ █ │ │  the left, tinted by goal ("52m").
│          │└────────────────────────┘ │
│ 11:00    │▓ Client call (Google)     │  Events unchanged.
│ 12:00    │ ┊Inbox cleanup  38m┊      │  Focus with no matching block: its own
│          │ ┊ unplanned        ┊      │  dashed block at its real time.
│ 14:00    │┌────────────────────────┐ │
│          ││Invoice design 14–15    │ │  Empty block: planned, not done.
│ 15:00    │└────────────────────────┘ │
└──────────┴───────────────────────────┘
```

Rules:
- **Planned** means a calendar item of type `task` or `habit_instance` with a time range on that day (never `countsTowardLoad`, which counts events). Calendar events (local, Google, Apple) are never planned work; they draw as they do today. In the wireframe: 9–11 and 14–15 are 3h planned; the 11:00 call is not counted.
- **Focus only.** Only sessions with `type = 'focus'` are drawn or counted; breaks never are.
- A session **matches** a planned block when it is on the same task and the same local date. Its minutes fill that block, whatever time of day they happened. The fill is the share of the block's length (capped at 100%; more focus than planned shows "+15m").
- A session on a task with no block that day, or on no task, is **unplanned**. It is drawn as a dashed block at its real time, labelled with the task title (or "Focus") and its length. Focus during an event's time is matched or unplanned by its task like any other.
- **Placement on the grid.** The day is the session's resolved local day (frozen `localDate`, or re-resolved from `completedAt` in the request `tz` for `localDateApprox` rows, exactly as the Time tab does). The end time is the frozen `localHour` plus the minute of `completedAt` in the request `tz`; approximate rows, and rows with no saved hour, use the request `tz` for both. The start is end − `durationSeconds`, clipped at 0:00 of that day. So a session saved in another timezone stays on the day and hour it happened there. A move between zones whose offsets differ by a non-whole hour can draw a block 30-45 minutes off (accepted, D3). A paused session draws later and shorter than its real span; accepted for v1 and stated in the sheet.
- **Overlap layout.** A dashed block joins `TimelineView.placeEntries` as a session entry (a union with calendar-item entries, rendered by its own branch), so it sits beside, never on top of, a task block or event at the same time. The grid, `hasAnything` and the empty-day messages count sessions too.
- **Tap targets.** Tapping a planned task block (filled or not) opens the task details sheet (`TaskStatsModal`, moved to `components/` and shared with Today), looked up in the task store by id. Its first row, "Focused <day>: 52m of 2h · 2 sessions ›", opens the existing `SessionsSheet` for that task and day. From the calendar, Load into timer and Mark complete work (a habit is ticked for that day); Edit is hidden (D1, D6). Tapping a dashed block opens `SessionsSheet` for its task (or "Timer, no task") and day. There is no separate hit target for the fill.
- **Tint** is the task's CURRENT goal colour, the same attribution the Time tab uses (`lib/goalAttribution.ts`), so a session has one colour everywhere.
- **Deleted tasks.** `GET /calendar` drops archived tasks, so if a scheduled task is deleted, its block disappears from past days and its sessions show as unplanned (titled from the session snapshot). Accepted for v1: past plan-vs-actual can shift after a delete. A unit test pins this behaviour.
- The header line counts: planned = sum of planned block lengths that day; focused = all focus sessions that day; unplanned = focused minus matched.
- A day with no plan and no focus shows nothing new. No guilt copy.

### Week view

Each day shows planned hours (outlined bar) against focused hours (filled bar), with "3/4h" under it. Tapping a day opens its Day view.

### Today

A one-line summary under the header: "1h 30m of 3h planned · 38m unplanned", with a thin bar. It is shown only when today has a plan or a session.

### Data and API

- **No new route. Extend `GET /time-report/sessions`** (`backend/src/modules/timereport/routes.ts`), which already filters focus sessions, resolves local days with `effectiveLocal` and attributes goals with `lib/goalAttribution.ts`. Today it requires `by` plus `key` or `none`. Change: when `by` is omitted (and so `key`/`none`/`cursor`), it returns every focus session in `from..to` for the caller, oldest first, not paginated, with the range capped at 31 days (Day and Week need at most 7; 31 leaves room for a Month view without another route change). Rows also carry `clientSessionId`. When `by` is absent, `key`, `none`, `cursor` and `limit` are rejected with 400, and the response is `{ sessions, truncated }`. Each row adds `startLocalMinutes` and `endLocalMinutes` (the placement rule above). The existing filtered mode is unchanged, so installed builds keep working.
- **Integration test (real DB), in the route's existing test file:** the unfiltered mode returns only the caller's focus sessions in range; a break session in range is excluded; another user's sessions are excluded; a range over 31 days or a backwards range is 400; no token is 401; a session finishing just after local midnight lands on the right day; a session saved in a different timezone than the request keeps its frozen day and hour; an approximate-date row resolves like `/time-report`; the filtered mode still behaves as before.
- **Pure functions in `mobile/lib/` with unit tests:** match by task and date, the unplanned remainder, the fill cap, the clip at 0:00, the empty day, events not counted as planned, and a deleted task's sessions becoming unplanned.
- **Calendar data: `useDaySessions(from, to)`** in `hooks/useTimeReport.ts`, used by DayView and WeekView. It merges the route's rows with the outbox's queued completions, de-duplicated by `clientSessionId` (D4), keeps only its last result while mounted, and refetches when the screen regains focus and when the timer store's delivery signal changes (set by `onSessionDelivered`; the outbox keeps its single handler). **Today's line** reads Today's existing local session history, the same source as its Focus today stat (D7). Both screens adapt their plan (Today: task store; calendar: `GET /calendar`) into one `PlannedBlock` list for the shared pure `planVsActual`.

### Error and empty states

Sessions loading: blocks render as today and fills fade in. Sessions fail to load: the calendar renders as today, with a small "Focus time unavailable · Retry" line in the header. Offline: queued sessions still show (D4); a range never loaded shows the error line.

### R2-1 — feasibility (blocking)

**Problem**

> The chosen refresh trigger fires before the server has the session. In mobile/stores/timerStore.ts, complete() and recordFocusSession() set lastCompletedSessionId synchronously, then submitSessionCompletion() enqueues the session in the outbox and flushes it asynchronously. A refetch of GET /time-report/sessions keyed on lastCompletedSessionId therefore races the POST and will usually return the day without the just-finished session, so Today's line (and the calendar) does not update after a session on Focus, which is the behaviour this text promises. The prior R1-8 obligation (Today refreshes when a focus session completes) remains unmet as specified.

### 1. Architecture

```
 GET /calendar ─────────────► calendar.tsx ──► DayView ──► TimelineView.placeEntries
                                   │                           ▲   (task blocks, events,
 GET /time-report/sessions ─┐      │                           │    dashed unplanned blocks)

        ▲                              ▲                               └──► Today line
        │                              │ refetch on focus + on
 timerStore.onSessionDelivered ──► sessionsDeliveredAt (signal) 
```

- Boundaries: the server owns the day/hour resolution (`effectiveLocal`) and the goal attribution (`loadCurrentGoals`). The phone owns matching against the plan, because the plan (calendar items) is already on the phone. One owner each.
- Security: the unfiltered mode keeps `WHERE s.user_id = ${userId}::uuid AND s.type = 'focus'` (routes.ts:394), so it is per-user and focus-only by construction. Integration-tested for other-user isolation.
- Production failure: the sessions request fails while the calendar loads. The calendar renders as today, and the header shows "Focus time unavailable · Retry" (design, Error states). Covered.
- Two shapes: (a) chosen: the server returns positioned sessions and the phone matches them to the plan in `lib/planVsActual`; (b) the server does the matching and returns fills and unplanned blocks. (b) would need the server to load calendar items and know which blocks are planned, duplicating `GET /calendar`'s rules (information leakage). (a) hides the matching behind one pure function `planVsActual(dayItems, sessions) → { fills, unplanned, totals }`. Pick: (a).
- Red flags: none in the chosen shape. Finding 2 (single outbox handler) avoided split ownership of the delivery hook.
- Findings: R1 (D3, approved A), R2 (D4, approved A), Scope Challenge 1-2 (carried). Dispositions: all accepted.
