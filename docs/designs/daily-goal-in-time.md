# Design: The daily goal becomes a time goal

Generated by /office-hours on 2026-09-04
Branch: fix/recurring-tasks-in-planning
Repo: Hafeezrahman735/pomodoro-app
Status: APPROVED
Mode: Startup
Reviewed: 1 adversarial round, initial score 5/10. Three factual errors found and
corrected below, including a migration that would have silently reset goals.

## Problem Statement

The app asks for a daily goal in **sessions** and counts progress in **time**. It
bridges the two by multiplying the session target by the DEFAULT session length,
which only holds if every session is that length. Sessions are sized to task
estimates (`lib/sessionPlan.ts` splits an estimate into 5-minute-granular blocks)
and the stopwatch records arbitrary durations, so they routinely are not.

Both of those paths call `recordCompletedSession({ type: 'focus' })`, so the
time-based side of the app is already correct. Only the goal is derived.

The same goal is counted two different ways across two surfaces:

| Surface | Where it lives | Counts |
|---|---|---|
| "Today's target" pill | Goal Progress drill-down (`activeView === 'goal-detail'`, `tasks.tsx:2166-2181`) | sessions: `Math.max(0, dailySessionTarget - sessionsToday)` (`tasks.tsx:1960`) |
| "Focus today" sublabel | main Tasks screen `PillStrip` (`tasks.tsx:1291-1320`) | time: `target x workDuration - focusSecondsToday` (`tasks.tsx:1286`) |
| Focus tab "Target left" | Focus tab (`focus.tsx:365`) | time |

**Worked example.** Target 8 x 25m = 200m. Four task-driven 50m sessions:
Goal Progress says **4 sessions left**; the Tasks strip says **Goal reached**;
the Focus tab says **Done**. Two surfaces say finished, one says half way.

They are not all visible simultaneously — Goal Progress is a drill-down — but a
user who checks their goal in one place and their progress in another gets two
different answers about the same day.

Two details that make the direction obvious:

- `settings.tsx:74` renders `8 sessions ~ 3h of focus per day`. The app states
  the conversion is approximate, then counts down against it as exact.
- `tasks.tsx:1962` already states the principle, for the weekly bars: *"Seconds,
  not session count: a 90-minute session and a 5-minute one are not the same
  amount of work and must not draw the same bar."* The daily goal breaks a rule
  the same file writes down.

Time is what the rest of the product measures: the leaderboard sorts on
`totalFocusTime`, the trace card shows FOCUSED, the profile shows hours.

## Constraints

`dailySessionTarget` is **client-only** — zero occurrences in `backend/src` or
`schema.prisma`. No streak, achievement, XP or leaderboard depends on it. It
lives in `timerStore` `Settings`, persisted device-level under `timer:settings`,
clamped `Math.max(1, Math.min(50, n))`.

Presentation-layer only: no server work, no schema change, no integration tests.
The only real risk is the values already on disk (see Migration).

**Out of scope, and NOT covered by this change:** `Goal.targetSessions`
(`schema.prisma:264`, rendered at `tasks.tsx:1332`) is a separate per-goal
session target that stays session-based. An earlier draft called the daily goal
"the last holdout of a session-centric model" — that was wrong; this one is not.

## Premises

1. The daily goal is set and counted in **one unit: time**. Nothing derived. — agreed
2. Existing stored goals are **converted, not reset**. — agreed
3. Client-only; no backend or schema work. — agreed

## Approaches Considered

### D1 — What unit
- **Chosen: time only, session framing dropped entirely.**
- *Time with a session hint while setting* — rejected: a hint derived from session
  length is one more value that can drift, the same shape as the bug being fixed.
- *Keep sessions, count sessions everywhere* — rejected: consistent but measures
  the wrong thing, the exact error `tasks.tsx:1962` warns about, and fights the
  adaptive-session feature that made lengths variable.
- *Two independent goals* — rejected: two ways to be "done" formalises the confusion.

### D2 — Implementation
- **Chosen: store `dailyFocusMinutes`, migrate once, and Goal Progress's "Today's
  target" shows the target itself** rather than a remainder.
- *Target pill shows remaining time* — rejected: it would then duplicate the
  "Focus today" sublabel, trading a contradiction for a redundancy.
- *Per-weekday targets* — rejected as scope creep.

## Recommended Approach

### 1. Settings shape
Replace `dailySessionTarget: number` with `dailyFocusMinutes: number` in
`timerStore`'s `Settings`. `DEFAULT_SETTINGS` gets `dailyFocusMinutes: 200`
(today's 8 x 25, so a fresh install is unchanged).

### 2. Migration — the part that must be right

**The naive version silently resets non-default users' goals.** Settings load as:

```ts
const settings = settingsRaw
  ? { ...DEFAULT_SETTINGS, ...JSON.parse(settingsRaw) }
  : { ...DEFAULT_SETTINGS };
```

Stored JSON holds `dailySessionTarget: 8` and no `dailyFocusMinutes`, so the
spread fills in `DEFAULT_SETTINGS.dailyFocusMinutes` = 200. A user on 50-minute
sessions with a target of 8 has a real goal of 400 minutes and would wake up
with 200 — half, silently, with no prompt. That is the exact failure this
document's own Assignment warns about.

So the migration must run on the **raw parsed object, before the merge**:

```
parsed = JSON.parse(settingsRaw)
if ('dailySessionTarget' in parsed && !('dailyFocusMinutes' in parsed)):
    parsed.dailyFocusMinutes = parsed.dailySessionTarget
                               * round((parsed.workDuration ?? DEFAULT.workDuration) / 60)
    delete parsed.dailySessionTarget
    AsyncStorage.setItem(TIMER_SETTINGS_KEY, JSON.stringify(parsed))   // persist NOW
settings = { ...DEFAULT_SETTINGS, ...parsed }
```

Three things this gets right that the naive version does not:
- it reads `workDuration` from the **stored** object, so the conversion uses the
  user's own session length rather than the default;
- it **persists immediately**, so the migration is idempotent and runs once;
- it **deletes** the old field, so the retired key does not live in the blob
  forever. Object spread does not respect the narrowed TS type, so without an
  explicit `delete` the field survives every future `saveSettings()`.

**This must be applied at BOTH load sites** — `timerStore.ts:544` (the no-`userId`
early-return path) and `:621` (the main path). Patching one leaves the other
un-migrated, which is a silent half-fix.

An earlier draft said to "follow the existing `LEGACY_KEYS` pattern". That was
wrong: `LEGACY_KEYS` moves whole top-level AsyncStorage keys and deletes them,
which is a different problem from transforming one field inside an existing JSON
blob. It is not a usable template here.

### 3. Delete the conversion
`dailyFocusTargetSeconds` in `lib/dailyTarget.ts` exists only to fake time out of
sessions. With the goal stored as time it has no reason to exist. Removing it is
what stops this bug class returning. `targetProgress` stays and now operates on a
real stored number.

### 4. Pickers and copy
Both surfaces set minutes, and all session-framed copy is rewritten:
- Tasks tab sheet (`tasks.tsx:1225-1243`): title "Daily Session Goal", body "How
  many focus sessions do you want to complete each day?", and the "sessions" unit
  label in `DailyTargetModal`.
- Settings row (`settings.tsx:65-80`): the `N sessions ~ Xh` subtitle becomes a
  plain time value. The `~` goes, because nothing is approximate any more.
- Steppers at `settings.tsx:79/92` and `tasks.tsx:1230/1243` change unit and bounds.

### 5. Pills — corrected map
There are two different strips, and an earlier draft conflated them.

**Main Tasks screen** (`PillStrip`, 3 tiles): TASKS DONE, COMPLETION (weekly
rate), FOCUS TODAY (with the to-goal sublabel). Only the sublabel changes.

**Goal Progress drill-down** (4 `TodayPill`s): Sessions done, Today's target,
Focus today, Tasks done. Only "Today's target" changes, from `sessionsLeft` to
the goal itself. `sessionsLeft` (`tasks.tsx:1960`) is deleted.

"Sessions done" stays. Counting how many times you sat down is an honest fact
about the day; it just is not the goal.

### 6. Focus tab
"Target left" reads `dailyFocusMinutes` directly. Colour semantics unchanged:
amber while remaining, `trace` when met, muted dash when no target.

### 7. Dead code found while mapping this
`noTarget` (`tasks.tsx:1285`) and `TargetState.kind === 'none'` are unreachable:
the target defaults to 8 and clamps to a minimum of 1, so it can never be zero.
The code says so itself at `tasks.tsx:1305-1308`. The new default is likewise
non-zero, so the branch stays dead. Prune it while in the area, or keep it
deliberately as a guard and say which.

## Picker Units — SETTLED

1. **Granularity and bounds: 15-minute steps, floor 15 minutes, ceiling 8 hours.**
   Fifteen minutes is the unit people use to talk about focus blocks and keeps the
   stepper short enough to scan on a phone. Eight hours is beyond a full day of
   deep work, so it bounds the goal without anyone meeting the limit in practice.
   The old range was 1..50 sessions, which at 25m reached ~20 hours; that ceiling
   does not survive being stated in minutes.

   Accepted cost: a 20-minute goal is not expressible, and neither is 40 or 50.
   If that bites, 5-minute steps are the fallback and would match
   `lib/sessionPlan.ts`'s own granularity.

2. **Display format: reuse `formatSeconds`** from `lib/calendarItems.ts`, which
   renders `3h` / `1h 15m` / `25m` and is what the trace cards already use, so the
   goal reads like every other duration in the app.

## Success Criteria

- Setting the goal and reading progress use the same unit on every surface.
- An existing user's goal is **converted using their own `workDuration`**, not the
  default: target 8 at 50-minute sessions becomes 400 minutes, not 200.
- The migration runs exactly once and leaves no `dailySessionTarget` in the
  persisted blob.
- Both load paths migrate; entering the app without a `userId` does not skip it.
- A user who only runs task-sized sessions sees a target that counts down correctly.
- `dailyFocusTargetSeconds` no longer exists.
- No pill duplicates another pill's number.

Tests in `lib/dailyTarget.test.ts`: the migration conversion at several session
lengths including a non-default one; idempotency (running it twice changes
nothing); a stored blob that already has `dailyFocusMinutes` is left alone;
`targetProgress` unchanged.

## Known Limitation, Disclosed

`globalTotalTime` (timerStore, incremented locally) and `focusSecondsToday`
(tasks.tsx, summed from `sessionHistory` after `mergeWithServerSessions`) are two
independently maintained tallies of today's focus time. On a multi-device day
they can diverge, so the Focus tab and Tasks tab could still disagree even after
this fix. Not caused by this change and not fixed by it. Worth its own pass.

## The Assignment

**Open Settings and read the subtitle under the daily goal**, then check your
session length on the Focus tab.

If your session length is not 25 minutes, the hours figure in that subtitle is
already the number the migration will adopt — and the review of this document
caught a version of the plan that would have given you 200 minutes instead of
your real goal. Confirm the figure you see is the commitment you actually want,
because after this ships it stops being derived and becomes the thing you are
held to.

## What I noticed about how you think

- You said the conversion "would not be accurate" because "different sessions
  have different times". Nothing crashes, no test fails, the screen looks fine.
  Noticing that a number is dishonest is a different skill from noticing that a
  screen is wrong.
- You overrode the recommendation. I argued for keeping a session hint to
  preserve the pomodoro mental model; you took the plainer version. The hint
  would have been one more derived value to keep in sync, which is the same shape
  as the bug. The simpler answer was the better one.
- You found this by connecting two features that live in different files:
  adaptive session lengths and the daily goal. Nothing on screen tells you those
  interact. That connection is the whole finding.
